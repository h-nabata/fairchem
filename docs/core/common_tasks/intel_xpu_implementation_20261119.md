# Intel Xe向け実装と回帰試験（2026年11月19日）

対象は `intel-xpu-fp32` の [e2aeefa](https://github.com/h-nabata/fairchem/commit/e2aeefa290e4800fc3c2976963f386a52a75d4ec) からの変更。下表の番号は同日の監査表に対応する。正しさを保つ変更は既存の入口に適用した。近似精度、重みの圧縮、タイル幅など、入力や機種によって有利・不利が変わる設定は個別に選択できる。

## 利用環境と確認できた範囲

- Linux x86_64・Python 3.12の空の環境に、専用パッケージをロックファイルから導入した。Torchは `2.15.0+xpu`、Intel Tritonは3.9.0。読み込んだ推論器がRayを要求しないこと、基本構成にCUDA Python・CUTLASS・nvalchemiが入らないこと、依存整合性を確認した。同環境で認識したXPUは0台だった。
- 小型UMAチェックポイントとCPU版PyTorch 2.15.0で、公開APIからの逐次予測、バッチ、学習時の逆伝播、力の差分や二階微分を検査した。モデル評価のテストでは、入力構造、重み、基準精度を揃えた。
- Intel TritonでのSPIR-V生成、CPUの実計算、ストリームやGPU番号を模擬する試験、実GPUでの試験は別の検査である。B70の定常速度、ピークVRAM、実ストリームの並行実行、配布チェックポイントでの化学精度は、下記の実機手順の測定対象である。

## 統合試験の結果

| 対象 | 成功 | スキップ | 選択条件による除外 |
|---|---:|---:|---:|
| Xe監査と周辺の回帰試験 | 2,300 | 61 | 57 |
| 上流から移植した物性回帰と追加試験 | 92 | 0 | 0 |
| 合計（同じテストを複数回数えない） | **2,392** | **61** | **57** |

Xe監査は[既存のテスト一覧](intel_xpu_runtime_test_paths_20261116.txt)に、新しいベンチマーク証跡、Pythonパッケージ、損失、LAMMPSのテストを加えた。メモリ上限内で完走するように別々のPythonプロセスで順に確認した。スキップと除外には実GPU、事前学習済みモデル、プロセス間通信が必要な条件などを含む。実LAMMPSは1 MPI rankで起動した。分散損失の不均一な有効件数は模擬rankで検証した。

物性回帰では小型のランダム重みUMAでCPU基準を生成し、同じ重みのFP32・FP64候補を採点した。別の重みに差し替えた候補が不合格になることも確認した。CUDA Nitroは5種類の入力で重みのdtypeとビット単位の一致を確認した。B70とCUDA上でのカーネル実行はこの集計に含めていない。

## 推論API、ASE・TorchSimと複数GPU

| 監査項目 | 反映内容と確認範囲 |
|---|---|
| R1 | TorchSimの初期化時に実効バックボーンの `otf_graph=False` または外部生成指定を検出し、空の辺での予測を防ぐ。実際のSimState変換と初期化拒否をCPUで試験した。 |
| R2 | ASEがローカル・並列・Ray Serve予測器のバックボーンからカットオフ、近傍上限、同距離近傍の扱いを取得する。CPUのpymatgen変換は中心原子ごとの全辺走査を1回のグループ化に変更し、非厳密な上限では内部UMAと同じ(k+1)番目の距離の二乗と許容差0.01 Å²を適用する。H–H距離6.5 Å、カットオフ7 Åの三原子系で辺数4、厳密上限1で辺数3を確認した。 |
| R3 | 非周期単原子のエネルギー、力、応力を設定dtypeで直接生成する。CPU FP64で参照値1+2⁻³⁰を保持する。 |
| R4 | MoLE統合時は既存モジュールのパラメータを直接統合する。全体再初期化と乱数を消費する線形層の新規初期化を削減した。モデル単体試験を参照。 |
| R5 | 共通の精度取得関数がPyTorchの新旧APIを扱う。XPUの厳密モードはoneDNNのtf32/bf16を検出し、B03は一時設定を例外時にも復元する。グラフや凍結radialテーブルのキーが新APIの使用時にも生成できる。 |
| R6 | 周期折り返しに検証・整数化済みの系番号を渡す。実際のTorchSimのint16入力とint64基準を比較した。 |
| R7 | 捕捉時の入力autogradノードが同じ寿命トークンを共有する。最後のテープ破棄または通常の逆伝播完了で再生を許可し、派生出力やretain_graphが残る間はワークスペースを保持する。CPU模擬グラフで破棄と遅延逆伝播を確認した。 |
| R8 | 明示バックエンドを持つプリセットで指定値が異なる場合は設定詳細を表示する。初回ログには設定、選択実行モード、実効バックエンドのクラス、Nitroの有無を記録する。個々のカーネルの採用は実機の検証対象となる。 |
| R9 | 厳密XPU呼び出しは読み取りを共有し、CUDA、Nitro、B03による精度変更とは排他する。CPUスレッド試験で2件の同時進入、書き手の待機、復元を確認した。 |
| R10 | 標準UMAのMoLEチェックをCPU由来メタデータの転送前に実行し、検証済みの厳密な組成キーを再利用できた場合は重複検査を省く。カスタムモデルのフックには従来どおりモデル側入力を渡す。 |
| R11 | 系IDと元素の結合インデックスから系ごとの絶対個数を一括集計する。整数メタデータはまとめてホストへ移す。均一バッチの個数は、バッチサイズに依存しないルータに限ってキーから省き、p-normの個数を保持する。 |

| R22 | 明示XPUでは公開ローダがNitro、CUDA専用モード、グラフv3、TF32、Series Bの制約をI/O前に検証する。FP64プローブ結果は同一公開呼び出しの構築中だけ共有し、直接構築時は改めて実測する。 |
| R23 | 単原子の参照経路をMoLE選択とモデル準備前に判定する。通常の単一系で複数原子があるときはテンソル形状だけで通過する。 |
| R24 | Series Bの有限性をデバイス単位でまとめる。TorchSimは出力dtypeに変換した後に検査し、変換由来のオーバーフローも検出する。 |
| D3 | ASEのラッパーが入れ子のAtoms.infoを専有し、同じ座標でもモデル入力メタデータの変更でエネルギーなどを再計算する。失敗時に以前の結果を公開しないよう和と寄与をまとめて更新する。 |
| K1・K11・K12との統合 | グラフ作成をプロセス内の共通ロックで直列化し、PyTorchの暗黙のcapture streamが別のGPUに属する場合はその形状・デバイスを通常実行に戻す。ウォームアップから捕捉終了まで動的トポロジーに安全な経路を使い、融合・高速算術の方針をグラフキーに含める。 |
| 上流 #2286 | Rayのactor登録とローカル推論から到達していたRayインポートを分散／サーバー経路に遅延した。新規プロセスでFAIRChemCalculatorをインポート後、rayがsys.modulesにないことを確認した。 |

CPUで確認した結果はグラフの実機再生、B70複数台の並行実行、カーネル時間、XPUピーク割当量の実測とは区別する。PyTorchが別デバイス用の暗黙ストリームを既に保持する場合、追加GPU上の捕捉は通常の評価にフォールバックする。

最終の対象CPUテストは415件成功、実アクセラレーターを必要とする4件はスキップ。別にNitroカーネルのCPUで実行可能な試験22件が成功し、CUDA専用1件を除外した。実機のoperator probeや配布重みを伴うレジストリ試験をこの件数に含めていない。メモリリーク検査はCPUの模擬テープ、RAII、保持出力、非同期境界を中心に確認し、長時間の実機計測は行っていない。

統合試験で、R10のフックを調べる一時変数がフォールバック時に古いモデルを参照し続けること、およびR8の追加情報で従来のログ行を解析できなくなることを確認した。フックの確認を短い関数に移してモデルの参照を返さず、ログに使うバックエンドはクラス名の文字列だけを保持する。プリセット名を示す1行目を従来の形式に戻し、同じログレコードの2行目にモード、バックエンド、Nitroの有無を記録する。古いバックボーンが再ロード前に解放されるかをチェック段階・forward段階の2通りで検査し、初回ログの既存テストを含めた3件すべてが成功した。

## UMA、MoLE、動径関数と微分

基準 e2aeefa。CPUの小型ランダムチェックポイントを使用。Xe実機での速度・VRAM・XPUカーネルの数値精度は未測定。

|元の順番|対応|
|---|---|
|1 portableの2回目の予測とキャッシュ容量|モジュールが明示した派生表だけをMoLE変更検出から除外。数式に使う非永続バッファの変更は引き続き検出。数値グラフの署名は派生表も追跡。予測後に派生ストレージを確認し、変化時に実容量を再計算してLRUの予算を適用。|
|2 inference_modeの初回energy後のforces|SO(2)のブロック重みと再利用可能な元素表を通常テンソルとして生成。CPUでinference_modeのenergyの直後にforcesを計算する公開APIの回帰テストを追加。|
|3 pnormの系数依存|実際の正規化関数を調べ、pnormはmerge整合性検査・キャッシュキーに系数を含める。単体系の後に同じ分子を二つ入力したとき、通常ローダーはフォールバックし、同じseedの未mergeモデルと公開energyが一致。|
|4 近似判定が異なる組成を許容|組成の比較を整数の交差積に変更。混合バッチ内・merge後再利用の両方でH377C233とH610C377を区別。UMA-S-1.2の絶対組成制約を維持。|
|5 FP64 Gaussian定数|既に線形層を置き換えたbackboneをそのまま使用。Gaussian係数はCPU FP64のロード前後で同値。小型チェックポイントでmerge・未mergeのenergyとforce normも一致。|
|6 radial重みの二重管理|準備したbackboneではpacked buffersに所有を一本化し、各層に残る未使用のrad_funcを解放。旧形式のprepared state_dictに含まれる重複重みを読み飛ばして従来と同じpacked値を使用。単体のUnifiedRadialMLPコンストラクタは元のモジュールから独立したスナップショットを作成。|
|7 LayerNorm→SiLUの勾配精度|backwardでnative_layer_normによる統計量を再計算し、同じnative_layer_norm_backwardを呼ぶ。通常のforceではネイティブSiLU勾配も使用。JVP・2階微分・保存テンソル削減をテスト。大オフセットFP32の通常一次微分はCPU native値と要素ごとに一致。FP64との差はネイティブFP32と同様に残る。|
|8 SO(2)変換コスト|メタデバイスでモジュール形状を作成。内部準備は元の線形層を移管し、ブロック重みを最終デバイスで初回に生成。公開変換関数は既存の独立コピー・即時使用仕様を保持。|

**試験の解釈** Intel Triton-XPU 3.9.0のコンパイラへ模擬BMGデバイス属性を与え、Wigner producer 2種・consumer残差あり/なしと、radial幅129/257をSPIR-Vまで検証した。ハードウェアの実行・速度・温度・ピークVRAM・学習済みモデルでの精度は測定していない。CPU上のTriton interpreterは比較マスクの要素型を保てない箇所があるため、追加の診断では比較結果をi1にする局所的補正を適用した。同診断ではランダム入力で投影あり/なしのproducerとconsumerの出力がTorch参照と一致した。この診断は配布コードを変更せず、Xe実機試験には算入していない。

二段集約追加前の単体・結合試験はCPU環境で364件成功、11件スキップ（13.50秒）。対象はWigner、CSR、radial、動径近似、圧縮特徴、低精度Linear、Series B設定と統合試験。リポジトリ指定のRuff 0.5.1による変更対象の静的検査も成功した。

二段集約追加後の限定試験は2件成功、Xe実機用1件スキップ（0.35秒）。Intelコンパイラは二段目の3構成すべてでSPIR-Vを生成した。分割を明示的に有効にした経路は次数と必要な部分和数をホストに読み出す。実機での時間比較には、この判定・区分構築・部分和の一時メモリを含める。

|小さいメタデータの転送|明示的なDeviceBatchStager(pack_small_tensors=True)で、256要素以下の整数・真偽値テンソルをdtype別のバッファへまとめる。転送元との所有権を分け、別の入力・メタデータのaliasを保持する。一般の可変メタデータを借用する最適化は行わず、所有済みバッチ契約を持つpredictorで重複コピーを除く。|
|GPU常駐collate|構造あたりの辺オフセットと原子数は座標shapeから計算し、バッチIDは全長を指定したrepeat_interleaveで一括作成する。CPUの小バッチではNumPy repeatを使い、CPU並列カーネルの起動を避ける。|
|Lanczos|基底とHVPの積を各1枚の作業行列に格納し、再直交化の内積は連続した行を参照する。列stackによる二重確保を除き、射影後・残差計算前に大きな行列を順に解放する。|
|反復HVP|座標のスナップショットをdetachし、既知の公開predictが所有コピーを行う場合は方向ごとのfield setだけ複製。外部predictorには従来の所有コピーを渡す。adapterが検査した入出力の重複cloneを除く。固定した勾配グラフは保持しない。|
|Hutchinson|probe_block_sizeでCPU乱数の生成順を保って転送をまとめる。既定のCPU FP64オンライン集計は同一サンプル順。device_block_statistics=TrueならデバイスFP64のブロック平均・分散のみをまとめてCPUへ転送・結合する。このモードでは丸め順が変わる。|
|直列DyNEB・緩和|共有predictorに画像ごとのFAIRChemCalculatorを構築し、モデルを一度だけロードする方法を明示。coarse/refineでは既存optimizer_clsでLBFGSを選択できる。どちらも既存の公開入口を使い、ASE結果キャッシュは画像ごとに保持する。|
|RESPA|history_strideに関わらず全外側ステップで最大ドリフトを逐次更新する。1は全履歴、正整数kは初期・最終とkステップごと、0は初期と最終を残す。|
|教師データ|生成済みCPUサンプルの所有権を内部で移し、公開コンストラクタは外部可変データを複製する。shard_directory・shard_sizeを指定すれば一時シャードに教師ラベルを逐次保存し、学習時にシャードを読む。ファイルを開くごとに独立したサンプルを返し、データセット全体のRAMスナップショットを省く。|
|蒸留の同期・転送|一度のto(copy=True)で所有移行。finite検査はパラメータごとのreductionをデバイス上にため、勾配と更新後重みについて各1回ホスト判定。元素表は参照値・デバイス・dtypeでキャッシュし、atomic_numbersをデバイス上でgatherする。エラー時に限り欠損元素をホストへ戻す。|
|蒸留checkpoint|share_ema_storage=Trueで生の重みとEMAのストレージをファイル内で共有し、同じParameterを複数名で登録した場合はkeep_varsとclone memoで対応する。extra_stateのコンテナとモジュールごとの版は保持する。既定は生の重み・EMAの変更を互いに分離する従来動作。|

CPU部品計測（同一プロセス、同じH₂入力、max_systems=1、5回の中央値、モデル評価なし）。128/512/1024/2048構造の計画時間はベース7.98/97.23/386.98/1816.12 ms、変更後0.09/0.35/0.82/1.43 ms。実機Xeでの転送時間・VRAM・エンドツーエンド速度の代用にはならない。

CPUの入力滞留量も独立した子プロセスで比較した。H₂と128 KiBの同一メタデータを1,000回投入し、各推論で1 ms待つ模擬予測器を使用した。開始時点からのプロセス最大RSS増分は旧125.91 MiB、新1.16 MiBだった。各条件1回であり、目的は先行投入による入力コピーの滞留を確認することにある。

検証はバッチ・AtomicData・サーバー・曲率・ワークフロー・蒸留のCPUスイートで257件成功、2件スキップ。最終追加／変更分の重点試験25件が成功した。両集計には重複がある。後者には実UMAを共有する直列DyNEB、LBFGS、参照表／ネイティブ単原子、別XPU ordinalを模した待機、結合バッファ、RESPA間引き、Hutchinsonのブロック分散、シャードとRAMの同じ学習損失、raw/EMA両経路・循環extra_state・共有Parameter・ファイルサイズを含む。XPU実機での速度、ピークVRAM、FP64ブロック統計のスループットは未確認。

## 物性回帰で照合する項目

- **異なるバックエンドの比較。** CLIのfullはXPUデバイスを受け入れても、最終報告が候補に基準機と同一のdevice文字列を要求していた。候補は起動時に記録したコミットとデバイスに照合し、検証用の既存ベースラインはそのアーカイブ自身のコミット、run_id、デバイス、設定に照合する。候補の各スイートに異なるデバイス・コミットが混在した場合も検出する。上流の旧設定にフォーク固有の追加フィールドがなくても、アーカイブの再検証は成立する。物理量の比較は同一スイート、チェックポイント、シード、計算計画、観測量定義、FP64参照ハッシュを維持する。
- **予測器とGPU番号。** ランナーは指定したCUDA/XPU番号をカレントデバイスにするスコープ内で予測器を作成して実行する。実際の予測器のデバイス種別と指定番号を照合し、ロード直後と評価後の両方で有効設定を確認する。ロード時の暗黙フォールバックが要求と異なる場合は計測開始前に終了する。失敗時もスコープから退出し予測器を解放する。
- **分割結果の取り違え。** CPUで集約するときに、各シャードのコミット、デバイス、設定、役割、スコープ、総数、番号、対象構造、変換名、実際の記録行を起動時の計画と照合する。全スイートのスモークと分割計算は既存の実行方式を使う。
- **性能値と測定環境。** XPUで記録する同期・ピークメモリ計測のプロトコルにXPUを明示し、CPUは同期なし・GPUメモリ未測定とする。CPU対アクセラレータの物性比較はGPUのピークメモリだけをペア比較対象外とする。数値判定に使う物理量には従来の欠測検査を適用する。異種ハードウェアの速度・メモリを同条件として格付けする変更はない。
- **実行元。** XPUパッケージのpyproject.tomlが存在するコミットでは、ソーススナップショットと作業ツリーの変更検査に含める。存在しない上流版も引き続きエクスポートできる。ローカル実行は呼び出し側が指定したHubのオンライン／オフライン動作とプロキシ設定を使用する。SLURMのオフライン実行は維持した。

CPU環境で、読み込み中の設定変更、アーカイブされた旧FP64設定の照合、候補と起動時のXPU番号不一致、明示番号の解析、新旧ソーススナップショットの5つの対象テストが成功。大規模キャンペーン、実XPU、公開ゲート付きチェックポイントと配布ベースラインを用いた物性値はここで計測していない。

## B70での実行と測定

リポジトリのルートから実行する。チェックポイントはHugging Faceから取得済みの同じUMAファイルを使用し、基準と候補でチェックポイントIDを統一する。通常の推論にはIntel専用パッケージの基本構成で足りる。物性回帰を実行する環境にはフォノン・弾性計算の依存も加える。

```bash
UV_PROJECT_ENVIRONMENT="$PWD/.venv-xpu" uv sync --locked \
    --project packages/fairchem-core-xpu --python 3.12 --extra regression
source .venv-xpu/bin/activate
python -m fairchem.core.scripts.validate_xpu --device xpu:0 --case periodic \
    --compare-merged --stress --fp64-reference --hvp --output b70-numerics.json
python -m fairchem.core.scripts.benchmark_xpu_batch --checkpoint "$CHECKPOINT" \
    --devices xpu:0 xpu:1 --output b70-dual.json
```

固定基準値を使う場合は、上流と同じ物性・構造の順序、チェックポイント、評価範囲を記録したbaselineファイルを指定する。通常のソースチェックアウトで実行し、基準ファイルとチェックポイントが別のモデルを指す場合は処理を中断する。

```bash
python -m fairchem.core.regression_suite fast xpu --device xpu:0 --run-on local \
    --baseline "$BASELINE" --checkpoint "$CHECKPOINT" --checkpoint-id "$CHECKPOINT_ID" \
    --suite prediction-fidelity --no-wandb
```

`full`で全対象構造を評価できる。`xpu-fp64`、`xpu-bf16`、`xpu-int4`、`xpu-int8`、`xpu-radial-table`、`xpu-fp64-saved-fp32`は別々の候補として記録する。固定組成の緩和・MDではE/Fと応力、NVEのドリフト、最大VRAMを揃える。反応経路では同じ始終構造で相対エネルギーと各像の力を比較し、振動・鞍点では同一座標でHVPを力の差分と比較する。GPUが2枚ある場合は1枚ずつの基準も採り、1系の待ち時間と複数系の総処理量を別々に評価する。

2枚のB70を登録したrunnerでは、リポジトリ変数 `XE_B70_CI=true` と `XE_B70_CHECKPOINT` で実機試験を有効にする。物性回帰も実行する場合は `XE_B70_BASELINE` に検証済みの基準ファイル、`XE_B70_CHECKPOINT_ID` にそのモデルIDを指定する。strict FP32、FP64、INT8の結果を別々のJSONで保存する。
